## Findings that changed the design

**Circle's USDC does not use clawback.** `auth_revocable: true`,
`auth_clawback_enabled: false`. The premise that regulated stablecoins carry
clawback — which the severity model was originally going to reason around — is
false for the largest asset on the network. Verified live before encoding
anything.

**`circle.com/.well-known/stellar.toml` returns 404.** The most reputable
regulated stablecoin on Stellar fails reciprocal SEP-1 verification by the
letter of the spec. This is the strongest available argument for keeping
accountability out of severity: had attribution been a discount, USDC would
score worse than a scam asset with a working toml. Reported honestly, not
special-cased.

**CAP-0035 makes `auth_revocable` a precondition for clawback.** Setting
clawback alone fails with `SET_OPTIONS_AUTH_REVOCABLE_REQUIRED`. So
"revocable + clawback" is not a suspicious combination, it is the only legal
way to have clawback. Severity became highest-single-capability rather than a
sum. Confirmed across 2,400 sampled live assets: zero have clawback without
revocable.

**Clawback is inherited at trustline creation.** `TRUSTLINE_CLAWBACK_ENABLED_FLAG`
is set when the trustline is created, so enabling clawback later does not reach
existing holders. This scoped the whole tool: Assay answers the *prospective*
question, and says so.

**A known scam with zero auth flags** (`DOGE-GA22IDJN…`). Capability analysis
honestly returns `clear`. It is the case that justifies keeping reputation as a
separate upward-only axis rather than dropping it for purity, and it is now the
most valuable subject in the eval.

## Decisions

- **Severity is capability-only.** No accountability discount at any level.
  Reputation escalates upward only. `base_severity` is kept beside `severity` so
  every escalation is auditable.
- **Checks do no I/O.** All fetching happens once in `scan`; checks are pure
  functions over a `Subject`. Tests need no network.
- **`get_safety` returns `Option`.** Never-attested must not read as safe.
- **The contract stores attestations, it does not scan.** Stated in the docs
  rather than hidden behind the function name.

## Known gaps

- No legitimately-clawback-enabled asset in the eval set. The most important
  gap: the claim that the model treats legitimate clawback fairly currently
  rests on structure, not measurement.
- No attestation-writer pipeline; the contract is not deployed.
- `evidence_hash` is stored but has no canonical encoding, so it cannot yet be
  verified independently.
- Horizon only; no RPC path, no testnet support.
